# Premium Digital Lounge — Phase 4 community and chat

## Implemented

The community overview now uses the existing uploaded/authorized cover in a large rounded hero with the real title, description, visibility, role and original join/leave controls. Ownership transfer requirements, invitation-only joining, memberships, records and stable URLs remain intact. Existing community posts/game-night links, member directory, invitations, role controls, header uploads, categories, overrides and audit history remain accessible. Owner/administrator settings have a real in-page anchor; moderators retain the existing scoped channel-management route.

A new authenticated overview read helper supplies privacy-permitted actual counts through the Phase 3 discovery summary, current membership, stored community guidelines and up to four recently active accessible text channels. Conversation metadata is read with the normal authenticated Supabase client through existing message/channel RLS, scoped to the community, nondeleted messages in the previous seven days and at most 80 recent rows. It returns channel IDs/names and message times, never message bodies, authors, emails or file paths. This list follows existing channel read access; it does not introduce a competing message history or rewrite existing chat/block semantics. Deleted/private/disabled channels remain subject to current policies.

Members see existing published global/current-community announcements, active LiveKit hangouts restricted to the current community and connect permission, community-filtered timezone-aware upcoming events, guidelines and a link to the real platform rules. Counts remain unknown when unavailable; no synthetic online members or engagement totals are added. Nonmembers receive permitted community metadata/counts and joining guidance, without guidelines/channel activity/events from this read helper. Missing access, identity or rate budget fails closed. Current membership is derived on the server; a client `member` prop is only presentation/optional-request control.

The secondary navigation reuses `CommunityChannelSidebar` with compact two-column overview/events/members/settings shortcuts to preserve drawer room for channels: overview, existing category/text/voice groups, events, Members, authorized settings/moderation, current-community picker and preserved unread/mention badges. Settings link to real controls rather than a visual-only button. Profile shortcuts, existing member-directory paging, private presence TTL and roles remain available in the right context/member panels; staff roles are now visible alongside names. Unknown/invisible status remains distinct from offline.

Chat colors, surfaces, selected/hover states, readable typography, reactions, threads, composer focus and member panes use the existing semantic lounge tokens in `premium-community.css`. No message-bubble redesign or altered message ownership is introduced. The original flex/viewport/virtualization/scroll boundaries, bottom composer, attachment pipeline, optimistic ID reconciliation, retry, private Broadcast topics, unread receipts, search, thread composers and permission checks are unchanged. The persistent member-layout LiveKit provider is unchanged; no second microphone stream or simulated room connection is created. CSS and additive read helpers do not replace the provider.

## Refresh and performance

- Overview metadata/room observations refresh about once a minute while visible and online, on connectivity restoration and existing community/access invalidations. Access-change handling clears prior overview content before a new authorized read. Request generations prevent obsolete responses from overwriting the new community. The user can retry failed activity reads.
- Opening text/voice channels does not mount the overview activity queries. Existing chat and channel/member subscriptions/polls retain their established lifetime and cleanup behavior. No message bodies or complete histories are loaded for the overview.
- Conversation reads are limited to 80 rows and four distinct channels. A busy channel can dominate that recent sample; this is not an exhaustive all-channel activity ranking. Counts reuse the existing 200-community summary and remain unavailable for a selected community outside that bound.
- Room observations reuse the actual LiveKit room service, filtered to up to 100 visible voice channels and explicit connect checks (at most six concurrent checks), current epoch and unlocked settings. Missing infrastructure returns unavailable. Room opening still obtains the original server-authorized token and worker enforcement.
- Scoped event reads reuse the existing endpoint; Home without a community argument keeps its original all-authorized-communities behavior. Scope changes clear prior event rows before loading new ones.

## Preservation and security

No migration, backfill, seed, community/channel/message deletion, attachment removal, role conversion or production data modification is part of Phase 4. Existing Phase 3 `community_discovery()` is optional for counts; missing statistics do not bypass membership or channel access. Existing Phase 10/11 event/announcement/guideline services and LiveKit configuration remain necessary for their respective features. Do not rerun prior installers solely for this visual release.

Every new server read validates community UUID and verified identity; it checks current `community_access`, budget and current role before reading member-only data. Normal authenticated RLS is retained for message/channel joins and guidelines. Voice checks current connect permission independently of the UI. No caller-selected actor, cached client role, arbitrary room grant or service-role data projection is introduced. Guidelines and labels render as escaped React text. Existing private banner/media URLs, file checks, moderation and account-isolation rules remain authoritative.

## Existing incomplete functionality / remaining acceptance

- Announcements reuse the existing component, which omits absent/failed results rather than distinguishing a separate empty/error banner. No fictitious announcement is displayed. Events refresh on mount/scope changes rather than a new live-event subscription.
- Nonmembers retain the existing global secondary navigation until they join; private channel/member navigation is not fabricated for an unjoined community. The community landing join flow remains real, with invitation-only spaces using the existing single-use invitation process. No new join-request approval state is claimed.
- No physical iOS/Android microphone, Safari, screen-reader, autoplay/background acceptance or sustained hosted load result is inferred from emulated Chromium/audio tones. Hosted worker uptime/access removal and canonical-domain deployment need their existing acceptance checks. No production-readiness declaration is made.

No new environment variables, accounts, storage buckets or Phase 4 SQL are required. Review/publish the local commit only with explicit release authorization; `main` triggers Vercel. Confirm Ready and perform hosted private-channel/media/two-device acceptance. Application rollback uses the prior deployment and leaves existing data/providers intact.
