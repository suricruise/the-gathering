# Faith Circles Phase 7 — visual Bible Study Builder

**Phase 8:** see [Scripture integration](SCRIPTURE_INTEGRATION.md) for the reference reader, private bookmarks and gated YouVersion setup, and the [completion/QA report](../FAITH_CIRCLES_COMPLETION.md) for verified results and remaining acceptance.

## Access and navigation

Open **Faith Circles → Leader Study Builder**, choose an authorized Circle, then **Create New Study**. Circle pages also show **Bible Study Builder** to current authorized teachers. Dashboard filters cover My Studies, Draft, Published and Archived; the workspace shows collaborative studies in the selected Circle with bounded pagination.

Access requires existing verified/onboarded/live Auth, current Circle membership and either approved primary leadership, an approved assigned co-leader, an approved community administrator under existing study permissions, or platform administrator/owner authority. No new identity, membership, leader self-approval or platform role is created. Platform administrators must belong to the Circle and pass its existing access restrictions; platform role alone does not disclose private Circles. Revoked approvals, archived communities, bans and existing blocks immediately affect fresh requests. Every read/write/upload is reauthorized server-side and in restricted database functions, not just the UI.

## Author a study

1. Create a draft using a stable request UUID. Set title, description, intended audience, topic, planned session count, study length and approved cover artwork. The audience field describes the curriculum; it does **not** override Circle access.
2. Optionally upload JPEG/PNG/WebP cover artwork up to **3 MB**. The server checks input size/type, actually decodes the image, rejects animated/vector images and re-encodes metadata-free WebP using the existing image processor. Covers stay in a new private bucket and use authenticated no-store reads, including on discovery cards. No public storage URLs or arbitrary remote cover fetching is introduced.
3. Add a session: title, passage reference, teaching, reflection questions, application, prayer prompt, optional leader-selected HTTPS media link and optional release time. The displayed local time zone is converted to an absolute timestamp; verify the displayed time when scheduling across daylight-saving changes. An empty release date means immediately after publication. Unpublished content is never scheduled into public discovery.
4. Formatting tools insert headings, bold/italic, ordered/unordered lists, safe links and validated passage references. A controlled text editor with a formatting preview reuses existing safe Markdown; there is no compatible rich editor dependency in the current application. Both member reading and preview use the same renderer. Raw HTML, arbitrary alignment styles, scripts, remote images and iframe/player embeds are not rendered. Supporting media is an explicit external link, never an automatic embed or server fetch. Content rights remain the approved author's responsibility.
5. Save study details and session drafts separately. Saves use serialized study revisions, stable session/question IDs and atomic question changes. Failed drafts remain in memory; no sensitive offline/localStorage queue is created. Closing/reloading loses unsaved changes after a browser warning. Reload status after an explicit conflict; do not overwrite another leader's work blindly.
6. Session summaries load in pages; individual lesson content loads on demand. Load all summaries before adding/reordering/duplicating so displayed order is complete. Duplicate creates new session and question IDs. Reorder swaps all existing identities transactionally without touching published responses or progress. Removing a draft question requires confirmation; the builder has no published-session deletion control.
7. Preview as member shows Read/Understand/Reflect/Apply/Pray/Gather, safe formatting and scheduled-release information. Preview is leader-only and never records visits, completion, answers or private reflections. Interactive answer/progress controls remain in the real published study room.
8. Confirm rights, then publish or submit for review. Planned session count must match saved sessions; every session needs teaching, application, prayer and at least one question. Publishing preserves stable IDs. Future sessions remain locked for members through all existing reading routes.
9. After publication use **Schedule linked Study Hangout** and choose the exact published session in the existing Phase 6 scheduler. No arbitrary room/token or second voice infrastructure is added. The reading room already displays authorized linked Hangouts.

Published editions remain immutable. Archive requires a reason and confirmation, closes member reading/discovery and existing Study Hangout admission, and preserves historical sessions, answers and progress. Create a separate new study for a revised edition; full published-edition cloning is not implemented.

## Review and featuring

Platform administrators can enable **Require independent platform review** for a Circle. Default false preserves the existing approved Circle-specific publication model; this is a new-study workflow policy, not a content migration.

Submitted/approved drafts are locked across the builder **and older session/question/detail APIs**. A platform administrator other than the submitter approves or requests changes with a reason. Withdrawal removes approval and reopens editing. New publication in a review-required Circle needs current approval; no browser role can bypass that database gate. Preview rights do not grant member completion or expose member reflections.

Public featuring requires platform approval. Approved Circle leaders can opt summaries into nonmember discovery or remove that consent under existing Circle visibility checks; they cannot newly feature a study. Existing featured historical records are preserved. Platform administrators can approve featuring from the published study's discovery settings. Private Circle visibility remains authoritative even for a featured study. Changing discovery consent never makes lesson content public.

## Data, files and audit

Additive version `202611230001_faith_study_builder.sql` extends `bible_studies` with intended audience/planned sessions and sessions with optional media links. Restricted review policy/status and metadata-only audit tables, authenticated cover mappings and a service-only orphan cleanup queue complete the workflow. Existing study/session/question/response/progress tables and historical data are retained. Scoped indexes support lists and recent history. Unique ordinal constraints are replaced with equivalent deferred unique constraints **within the migration transaction**, allowing safe swaps while preserving uniqueness and all records. No community/user/message deletion or reset occurs. Revalidating these unique constraints briefly locks the study tables: inspect table sizes and use a suitable low-traffic migration window.

Recent builder history shows the last 30 metadata events (operation, revision, time); trusted administration retains actor identities in protected audit records. No prayer, private member answer/reflection, credentials or copied voice media is added to these records. This is not a full body-version restoration system. Review feedback is visible only to authorized editors. Existing community audit events continue recording sensitive operations.

The `faith-study-covers` bucket must remain private with no browser object writes. Route handlers validate current draft permission before upload and again during assignment; GET checks current study/summary eligibility before server-only download. Interrupted/replaced/deleted files are tracked in the private cleanup queue. Schedule **`npm run faith:covers:cleanup`** daily in the existing trusted maintenance environment with server-only Supabase settings. It removes only unreferenced queued paths older than 24 hours, at most 100 per pass; repeat for backlogs. Published study artwork may remain with retained study records after author deletion, but existing creator/Circle eligibility still restricts reading. No new personal uploads are copied into unrestricted activity feeds.

## Installation and rollback

Production SQL/deployment needs separate approval. Verify backup and migration history through Phase 6 `202611220001`, then run only **`supabase/faith-study-builder-setup.sql`** or its matching versioned migration via normal tooling. The installer skips recorded versions and refuses ambiguous unrecorded objects; do not reset tables or manually mark unverified history applied. A `pg_advisory_xact_lock` result is normal. No new third-party secret/editor/Bible license is required. Existing canonical `APP_URL`, Supabase credentials, LiveKit provider and enforcement worker stay in place.

Keep additive tables, privacy triggers, private bucket and safe unique constraints on an application rollback; do not drop studies or participant data. An older UI may receive an honest permission error for newly locked drafts or unapproved featuring. Restore backups only using the existing documented recovery process. Local test-stack history can differ from Supabase installer history: inspect both ledgers rather than replaying original phase installers over existing objects.
