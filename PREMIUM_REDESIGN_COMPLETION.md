# Premium Digital Lounge — final QA

Review date: October 26, 2026 (America/New_York). Baseline: `9b15c6d`. This is a review and regression-fix milestone in the existing application, not a replacement app. Production data and deployment were not modified.

## Design reference and scope

Compared the implementation with the approved reference and `GATHERING_PREMIUM_REDESIGN.md`: narrow community rail, purple secondary navigation, midnight-blue main workspace, contextual right column, rounded visual community cards, restrained cyan/magenta accents, real member identities and accessible responsive drawers. The Gathering's brand, tagline, faith identity and gaming features are retained. Reference photographs, avatars, logos and illustrations were not copied; original CSS artwork and existing authorized uploads are used.

The current implementation includes the earlier shell, Home/Explore, community/chat, Hangouts and profile/discovery milestones. This QA does not imply a separate, unrequested bespoke redesign of every social/event/admin form. Those areas retain their existing functional components inside the premium shell and shared semantic form/panel styling. Public auth/legal/install pages retain the earlier dark visual treatment.

## Changes made during this QA

1. **Voice/text boundary:** ChannelWorkspaceLayout was sending voice IDs to `chat_save_navigation`, whose database guard correctly accepts text channels only. This caused the previously documented navigation-preference warning and exposed text-message search/notification settings inside a voice room. Voice rooms now omit those text-only controls and visits; no database guard or LiveKit grant is weakened. Shared category preferences can be saved through a currently accessible text channel without replacing the saved last text channel. In a voice-only community, category toggles remain local; remembering a last voice room is not implemented by this text-navigation API.
2. **Persistent-layout data loading:** The authenticated shell previously fetched the full profile editor bundle—six queries including preferences, game/platform selections and both catalogs—just to display identity. It now loads the authorized minimal profile identity in one query. Editors/onboarding still load their full data. No shared/public cache, new provider, auth bypass or new migration is introduced; missing identities fail closed.
3. **Contrast and layout:** Home/Explore and Hangouts hero body text sat directly on bright gradient stops (unprotected token-stop contrast approximately 1.72–3.68:1). Applied the existing semantic scrim above decorative artwork and below copy. The browser test calculates a conservative contrast bound from actual computed foreground/scrim colors, even assuming white artwork underneath. The flat People heading also inherited an inappropriate horizontal heading/action flex layout at tablet/desktop widths; it now stays vertical. These are scoped styles, not a new page architecture.
4. **Regression test maintenance:** Updated pre-redesign cover assertions to verify actual authenticated image sources instead of obsolete CSS backgrounds. Community-order tests scope Home's My communities section and the discovery grid because the same community can legitimately appear in several curated Home sections. Existing private-file, order, confirmation and audit assertions remain.
5. **Repeatable visual/performance evidence:** Added browser capture/axe/overflow/image/composer checks for major routes at 1440, 1024 and 390 pixels, real network delay/failure/offline recovery cases, and an isolated 5,000-row query-plan probe. All seeded content is explicitly local QA content. No production member statistics are fabricated.

## Executed results

- Lint and TypeScript checks passed after the fixes.
- Full unit suite: **365 tests in 65 files passed**, including the new text/voice boundary, category-save and fail-closed minimal identity tests. The first new component-unit run exposed jsdom's missing native dialog API; a test-only native-dialog stub fixed that environment gap. Production dialog behavior was not replaced.
- **431 checks passed across 28 local service commands**, including six voice-worker tests. Commands: profiles:lounge, communities, community:headers, community:management, workspace, messaging, interactions, threads, chat:reliability, chat:navigation, channels:management and setup, people, members, people:rail, members:rail, spaces, admin, social, squads (including ten simultaneous-join checks), discovery, lounge, launch, real chat/People/space Realtime, voice and voice:worker.
- The local query-plan probe passed: a 5,000-message private channel returns forty initial messages. See the measurements below. Its first test draft used an obsolete `items` response property; it now checks the actual `messages` contract. That draft was not counted as a passing check.
- Production build and production `next start` were executed successfully before the browser review. The completed production build/`next start`, configured client-bundle secret scan and tracked source/history credential-pattern scan pass. Scans cover configured/recognized patterns, not every possible credential format.

The broad functional browser run passed **122/122 in 19.0 minutes** against the production build containing the text/voice and minimal-identity fixes. The complementary captures/header/order cases passed **6/6**; network-state cases passed **2/2** after harness corrections. That establishes **130 distinct passing browser scenarios across complementary runs**, not a claim that one initial all-suite command passed cleanly. After the final Hangouts/People CSS refinements, the eight affected visual/state/People/Hangouts cases passed **8/8 in 2.7 minutes** on the completed production build. This includes re-capturing every page at all three widths; the hero contrast and vertical heading checks pass. See [verification.json](docs/qa/premium/verification.json) for sanitized run counts and service commands.

For transparency: the initial baseline was deliberately stopped after **58 passes, two stale cover/order assertion failures and 68 unrun cases** to rebuild with the fixes. Those unrun cases are not passes. The first network-state harness removed a held route before its callback finished; it was corrected to wait for active handlers. A subsequent exact text locator incorrectly expected a status paragraph to exclude its Retry button; selecting the actual status by its full message resolved that assertion. Both real network-state cases then passed without altering app error handling or fabricating responses.

## Performance findings

- Message history remains paginated in forty-message pages. Existing 5,000-row browser tests check virtualized DOM bounds, older-page anchor preservation, incoming messages while scrolled up and reconnect catch-up exceeding four thousand rows. Both desktop and mobile long-history/reconnect cases passed in the 122-case functional run.
- [`query-performance.json`](docs/qa/premium/query-performance.json) records an executed local warm-cache sample after refreshing planner statistics on the isolated fixture: indexed root page uses `messages_root_page`, returns forty rows, approximately **0.034 ms** execution and four shared buffer hits; authenticated conversation RPC approximately **30.677 ms**. A first sample with stale fixture statistics selected a broader FK index and took approximately 24.715/126.453 ms respectively. This demonstrates the importance of representative statistics; it is not a production benchmark or authorization bypass. No hosted ANALYZE or production SQL was performed.
- Final local navigation observations across eighteen routes per width: TTFB medians approximately **151 ms desktop / 113.5 ms tablet / 114 ms mobile**; observed ranges 56–552 / 64–401 / 63–452 ms. Slowest DOMContentLoaded observations were approximately 1,508 / 727 / 874 ms. These are local hard navigations under the test workload; full capture durations include axe/screenshots and must not be described as SPA transition times or production p95. See the linked timing JSON for individual pages.
- The shell now performs one identity query instead of six editor-bundle queries. This is a concrete reduction in unnecessary reads, not a claimed measured production speedup.
- Source review confirms memoized message rows, stable callback/ID reconciliation, bounded attachment/receipt projections, virtualized long timelines, coalesced realtime invalidations and timer/listener/subscription teardown. The cleanup browser case observes actual WebSocket closure, not just unsubscribe calls. No React profiler/hosted CPU trace was executed; absence of unnecessary renders is not certified from source alone.
- Discovery/Hangouts/recommendations are bounded but still do per-community/access and activity work. Shared snapshots/large hosted query plans/production network latency and sustained concurrent media remain operational follow-ups. Avoid public caching of authenticated responses as a shortcut.
- Community card images use lazy/async loading; private covers/avatars/files retain authenticated no-store endpoints. Uploads retain validated resizing/re-encoding and size/type/ownership controls. Responsive source variants and authenticated thumbnail derivatives remain possible future optimizations.

## Incomplete features and known limits

- No light theme is implemented. No fake theme control was added.
- Separate physical-device microphones, iOS Safari/Android/installed-PWA keyboards, headset/autoplay/OS-background behavior, screen readers and 200% zoom require manual acceptance. Chromium touch/viewport tests and real generated capture tones do not certify hardware or mobile operating systems.
- Temporary general member-created Hangouts and durable/cross-device recent-room history remain documented extensions. Recent successful rooms are current-tab state only.
- Profile covers use original CSS artwork; profile-banner upload is not implemented. Full interests require explicit sharing; anonymous public profiles do not gain a new member-list/preferences endpoint.
- Broad profile interests and historical social tags retain separate database contracts. No unsupported new social filter is advertised.
- Voice-only communities retain local category toggles and the existing last-text-channel navigation contract; no new voice navigation preference schema was added.
- Some right-panel suggestions/new-member lists can still be loading briefly after the main page is ready; explicit loading/unavailable states are retained. Persistent-shell identity reads are reduced, but secondary server-action latency deserves hosted measurement.
- Public/PWA metadata and some gaming-first copy retain earlier wording/visual assets; a separate coordinated public/install/social copy pass remains appropriate.
- Several inner social/event/DM/notification/settings/admin screens retain earlier component composition, with premium shell/tokens. Further bespoke visual redesign is a future scoped milestone, not silently claimed completed here.
- No hosted migration/deployment/configuration was verified by this local QA. Existing new-member, discovery and profile database updates must be installed in the target environment; do not rerun old phase setup or reset tables. Canonical APP_URL, Supabase private storage/Realtime, LiveKit credentials and enforcement-worker freshness remain deployment prerequisites.

## Security and launch assessment

Existing Auth, stable user/message/channel/community IDs, RLS, server-derived identities, private authorized Realtime, blocks, post/connect distinctions, platform/community role separation, moderation evidence/audits, secure attachment endpoints and persistent LiveKit provider boundaries are preserved. New fixes do not loosen channel guards, expose moderator controls to members or grant arbitrary room access. No production database operation or deployment was authorized/performed by this milestone.

This report does **not** declare unconditional production readiness. Local automated coverage must be considered alongside the remaining physical-device, hosted-scale/configuration and product limitations above. Release only after review/approval and hosted acceptance, with the existing backup/recovery and rollback procedures.
