# Premium Digital Lounge — Phase 3 Home and Explore

## Experience

Home and Explore reuse the authenticated Phase 2 shell, existing routes, community directory order, joins, protected uploaded banners and membership permissions. The hero uses original CSS abstract orbital art and the exact supplied headline/supporting copy. No proprietary reference assets, generated members, invented engagement, new chat provider or replacement voice infrastructure are introduced.

Home includes active authorized LiveKit hangouts, channels with recent committed conversations, upcoming activities through existing timezone-aware events, featured large cards, smaller popular cards, ten interest links, permitted recent published community posts, newly created public communities and joined communities with real unread indicators. Existing Squad Up, Faith & Life, event dates, social feed, installation and policy links remain. The shell supplies the current profile, privacy-filtered new members, friends/activity and recent relevant invitations from the member's latest 30 permission/preference-filtered notifications. “All notifications” opens the existing full invitation/response workflow.

Explore preserves text search and All/My communities filters, adds combinable interest filtering/deep links, visual cards and public join actions through the existing `community_command`. Discoverable/invitation-only spaces still require the existing invitation process. This phase does not invent a pending-approval membership state or send unsolicited requests to hosts. Private communities remain hidden until access is granted. Only existing owners/administrators or platform administrators can set an optional interest category; changes are validated inside the existing administrative transaction lock, rate-limited and recorded in community and protected platform audit logs.

## What the numbers mean

- **Featured:** first two accessible directory records in existing administrator-controlled `display_order`, name, UUID order. This is curated ordering, not an undisclosed recommendation model. Existing ordering is preserved.
- **Popular right now:** accessible non-private communities with positive activity, ranked by the sum of up to **500 committed, nondeleted messages** and up to **500 accessible published community posts** created during the previous **seven days**. A message counts only when the caller currently has channel access and its author is active and unblocked; a post must pass existing `post_access`. Private channels never affect an unauthorized caller's score. Replies count as messages. Ties use curated directory order, name and UUID. The score is a capped ranking signal, never displayed as an exact global engagement total. The result is personalized by access, not comparable across viewers, and excludes private communities even if the member belongs to them.
- **Members:** actual active, live membership records excluding mutually blocked accounts. Counts can differ between viewers and are not a public account directory.
- **Online at refresh:** only available to current community members and only counts active, unblocked members whose existing `private.people_card` permits online presence under its privacy/freshness rules. Hidden status is not treated as proof of offline; outsiders get `null`, not zero. This is a snapshot, not a new presence system.
- **Live conversations:** authorized text channels with a committed, nondeleted, live/unblocked author's message in the last **15 minutes**, most recent first, at most four. No message body is returned in this list.
- **Active hangouts:** actual LiveKit `numParticipants` matched only to up to 100 RLS-visible voice channels with current `connect` permission and unlocked room settings. Zero-participant rooms are not presented as active. Missing credentials/network/room service failure shows unavailable; no fake counts or simulated successful connection. Opening a room retains the existing token endpoint, permission enforcement and persistent provider.
- **Recent community activity:** at most four published community post excerpts from the last seven days, each passing current `post_access`. No private prayers, DMs, deleted/hidden posts, or unauthorized files are read. Text is escaped by React.
- **Recently added:** newest creation dates among public communities in the accessible directory. Discoverable and private records are excluded.
- **My communities:** active existing memberships, with the existing authorized unread projection. No unread zero is fabricated if the discovery projection is unavailable.

Home snapshots refresh approximately once per minute while visible/online, on restored connectivity and after existing access/community invalidations. Access-change events clear activity before refetching. The rail and actual chat subscriptions retain their independent established behavior. Hangout observations refresh once per minute; going offline removes live counts. The page explains snapshot semantics. The directory remains bounded to the existing 200-record API; cards describe this limit and discovery does not claim to search unseen records.

## Taxonomy and data preservation

`202611140001_discovery.sql` adds a nullable `communities.interest_category`, checked against the ten supplied slug values, plus two read projections/actions and two recent-activity indexes. Existing communities are **uncategorized** until a host makes an explicit choice. No keyword inference, default classification backfill, role change, message/member deletion, reseeding or provider replacement occurs. The existing community detail query tolerates the missing optional column during rolling deployment.

The authenticated `community_discovery()` projection checks live identity, current access, blocks, visibility and status inside PostgreSQL. Anonymous execute is revoked; reads have a 120/15-minute budget. The application uses its normal authenticated client; service-role credentials do not reach clients. Statistics expose counts/IDs, not private membership rows, email, exact member activity times or Storage paths. Native lazy-loaded cover images continue using protected existing banner endpoints and preprocessed uploads; no third-party artwork/previews are fetched by this phase. Category input is independently validated by Zod/allowlist and database constraints/authorization.

## Installation and rollback

No new environment variables, buckets or third-party accounts are required. Only the isolated local stack was migrated during implementation.

1. Obtain release/production-SQL approval. The current implementation task does not publish or deploy.
2. Install only pending version `202611140001` using the existing migration pipeline, or run the complete `supabase/discovery-setup.sql` in the intended Supabase SQL Editor. Phase 2 new-members setup must already be installed. The installer checks prerequisites, skips recorded reruns, and refuses objects without a migration record. Never rerun all old phase installers, delete communities, reset tables or mark an unverified migration applied.
3. Verify signed-in counts/category reads and private-channel/anonymous/blocked/suspended denials in the intended environment. Choose interest categories under each community's existing **Community settings → Discovery interest**.
4. Publish the reviewed commit through the existing Vercel main-branch process and confirm Ready/canonical-domain functionality. Recheck two accounts and real-device voice permissions. A Git push alone does not establish successful deployment.
5. Application rollback uses the previous deployment. Leave the additive column/functions/indexes in place; previous versions can coexist. Prefer a forward correction. Destructive removal, schema reset or member preference/data restoration requires separate review and backup procedures.

Missing/limited discovery services leave the directory searchable with existing memberships and covers, while explaining that counts/categories/activity are unavailable. No fake production data fills the gaps. Route-specific loading panels, honest empty sections, existing retry/error boundaries and unavailable LiveKit/notification states are retained.

## Remaining limitations

Physical iOS/Android keyboard and screen-reader acceptance, hosted installation/release verification, long-running worker/LiveKit availability and sustained large-community load remain separate acceptance. Community counters and unread aggregation can scale with visible membership/history; recent message/post indexes support the new time predicates, but this phase does not claim hosted query latency or add shared caches of private data. The ranking is capped and directory-bounded; a future cursor-based discovery API and incrementally maintained, permission-aware summaries would be needed beyond the existing 200-community cap. No new true join-request state, exact online total for privacy-hidden members, proprietary artwork or AI-generated activity is claimed.
