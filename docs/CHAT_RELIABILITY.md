# Stage 6 — chat reliability audit and implementation

## Initial audit (before implementation)

The existing Supabase PostgreSQL/private Broadcast provider is suitable and is retained. Persistent messages commit before ID-only events, writes use stable UUIDs, reconciliation compares exact bigint versions, channel epochs rotate on access changes, and server/RLS checks protect reads/writes/files/subscriptions. Stage 5 threads share that same authorized channel transport. Existing typing is throttled, ephemeral and server-originated; presence is preference-gated and expires after 90 seconds.

Issues found in source:

- The composer waits for an HTTP result and has no visible optimistic timeline row. A lost response can leave an uncertain attempt locked even after an authoritative live copy arrives.
- Catch-up and receipt events fetch the latest 40-message history repeatedly, including when only read metadata changed. Trailing-edge debounce can starve work during continuous events.
- Failed connections can wait for the 30-second session interval to retry. Several asynchronous fetch paths lack a lifecycle/access generation check, so an authorized response started before revocation could merge after the UI was cleared.
- The large-backlog catch-up fallback replaces cached messages with the newest page and skips the rest of the revision stream. That can discard loaded thread/history context.
- Initial channels always preload the newest 40 roots. An older first-unread message cannot anchor the opening view. Read marking is not directly reevaluated on focus/scroll and must not advance for hidden/background or unrendered messages.
- There is no New Messages affordance for someone reading earlier history. Scroll handling relies on message-array changes, and rich-media height changes or prepends need explicit anchors/follow rules.
- Loaded message rows and sorting/render work grow without a bound. Thousands of explicitly paged messages require measured list virtualization rather than an always-mounted history.
- Mention badges count unread notification records even after their messages have been read in the channel; channel and mention read state can disagree.
- Channel navigation counts poll rather than receiving private cross-device read/message invalidations. Receipt updates are channel-scoped, so another device viewing a different channel waits for polling.
- Presence privacy and server expiry already work, but foreground/online return does not pulse immediately; cached online indicators can survive failed/background polling indefinitely. Stale data must be labeled unavailable rather than invented offline/away status.

The implementation and final verification record below will distinguish actual local multi-account tests from hosted/physical-device/load acceptance. No provider replacement or production data reset is authorized by this audit.
## Implemented behavior

- Retains Supabase PostgreSQL and private Realtime Broadcast, stable message UUIDs/revisions, channel epoch authorization, secure files and the persistent LiveKit boundary. No communities, histories or identities are replaced.
- Optimistic rows are separate local delivery records, never fake persisted messages. HTTP results and authorized saved rows settle the same UUID. Uncertain retries keep their original payload/ID; definite rejections allow correction. No private drafts/outbox are saved by the service worker.
- Reconnect uses bounded exponential retries, session reauthorization and generation checks on asynchronous responses. Revision catch-up runs at most five 200-row pages per turn and schedules further turns until caught up; it never skips a watermark or replaces loaded history to recover a backlog. Changed events use a first-edge debounce rather than waiting for continuous traffic to stop. A ten-second metadata-only check repairs missed invalidations; histories are fetched only if its revision is newer than the local cursor.
- Unread channels open at an available first unread root; read channels open at the latest roots. Initial, older, newer and latest projections return at most 40 roots. Older/newer navigation preserves a reading anchor. Automatic following requires proximity to the actual tail; New Messages / Jump to latest provides an explicit return. Thread panes retain their independent anchors and composers and expose a latest-reply jump.
- Measured TanStack Virtual rows activate above 120 loaded messages/replies, with stable keys, overscan, dynamic heights and end anchoring. Shared targets remain mounted for deep links. Small histories retain normal document flow and keyboard controls. Reconciliation retains unchanged references, and message rows are memoized.
- Receipts fetch only channel metadata and at most 100 displayed message IDs, not complete histories. Focused, visible main-chat reading advances only through a visible committed root after a short debounce. Hidden panes, pending sends and background pages do not advance receipts. Explicit Mark read acknowledges the whole channel, including unloaded/thread activity; reading a thread alone conservatively does not mark unseen roots read.
- Existing private personal topics carry generic chat-summary invalidations to refresh only authorized community unread/mention counts across devices. The application payload is empty; the installed Supabase Realtime service adds a generated delivery-event UUID. No channel ID, message ID, content or history is included in these personal summaries. Mention badges also respect the channel receipt while retaining existing notification consent and access filters; the notification center remains independently acknowledged. Channel events retain existing ID-only committed invalidations.
- Typing stays server-authorized and ephemeral, with a three-second client throttle, six-second server expiry, immediate stop removal and multiple names. Existing server budgets remain enforced.
- Presence keeps the existing preference-gated server projection and 90-second activity expiry. Foreground/online returns pulse immediately subject to a 15-second throttle. Rosters refresh every 15 seconds; a cached status older than 20 seconds or an offline viewer shows Status unavailable instead of leaving a stale green dot or inventing an offline state. Opt-outs remain Status hidden; no private activity timestamps or public presence channel are added. Optional away status is deferred.

## Database and release procedure

1. Review the additive migration `supabase/migrations/202611100001_chat_reliability.sql` and ensure Stage 5 (`202611090001`) is installed. It adds read RPCs and summary triggers and updates the existing mention-count projection; existing message/storage/RLS models and indexes remain.
2. Obtain explicit approval before modifying hosted Supabase or deploying. This implementation applies SQL only to the isolated local stack.
3. With the normal versioned migration workflow, apply only the pending version. For the SQL Editor workflow, use `supabase/chat-reliability-setup.sql`, not an older phase installer. The installer takes a transaction lock, records its version and skips a recorded rerun. An ambiguous object/history mismatch stops safely for inspection. `pg_advisory_xact_lock` output itself is normal.
4. Verify `chat_state`, `chat_conversation_page`, `chat_receipt_snapshot`, `chat_mark_all_read` and `chat_community_state` exist with authenticated-only grants. Confirm private personal-topic policies and Realtime Broadcast remain enabled; there is no new public topic or new secret/environment variable.
5. Deploy the reviewed application only after migration approval/application. Verify the canonical APP_URL, two-account live delivery, privacy/revocation and live voice on the deployed build.

Rollback: prefer rolling back the application first. These additive functions/triggers can remain safely with the prior app. If removal is required, a reviewed follow-up migration should remove only `chat_summary_message`, `chat_summary_receipt` and the six Stage 6 functions after checking dependencies; do not delete messages/receipts, reset Supabase, edit published migration history, or remove provider-owned Realtime objects. Restore backups only through the existing recovery procedure.

## Performance and operational limits

Existing `messages_root_page`, `messages_history`, `messages_changes` and thread activity indexes serve root/directional/revision paging; no duplicate index is added. Unread metadata still counts eligible rows, and personal-summary/notification fan-out scales with authorized membership. Virtualization bounds mounted DOM, not the JavaScript cache of explicitly loaded rows. Extremely long continuous sessions and very large communities still require measured load acceptance, query/egress monitoring and possibly a separately reviewed cache/window or summary design. No throughput/production-scale certification is implied by local tests.

Private reads/writes/subscriptions remain independently authorized. Access changes rotate topics, temporarily block merges/posting and reauthorize; confirmed denial clears cached timeline, pending sends, typing, thread/search views and prevents stale-response resurrection. Files retain authenticated routes and private storage. Rendered Markdown never trusts HTML. Temporary reconnect failures retain existing readable context with a visible status; they never manufacture delivery, presence or voice success.
