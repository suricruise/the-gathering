# Premium Digital Lounge — Phase 2 application shell

## Implemented scope

The existing authenticated application now has a narrow joined-community rail, a purple secondary navigation slot, a flexible midnight-blue workspace and an optional contextual activity panel. It retains Next.js routes, Supabase Auth/PostgreSQL/private Realtime, existing community permissions and the persistent LiveKit provider. No communities, memberships, messages, roles, uploads or channel IDs are recreated.

- **Community rail:** own Gathering mark, Home/Explore, authenticated active joined communities, existing protected headers or cover/initial fallbacks, current-community selection, actual authorized unread indicators, named/tooltipped controls, scrolling, discover/add and incremental loading (30 initially, existing backend cap 200). The selected community is included even outside the first page. Unavailable unread data remains unknown, not a fake zero. Community opening reuses the existing validated remembered-channel switch.
- **Global navigation:** Home, Explore Communities, Hangouts (`/voice`), Gatherings (`/events`), Announcements, My Communities, Messages and all existing Text channels/Members/Squad Up/Social/Faith/profile/settings/admin destinations. My Communities uses a real joined filter; search submits a real community query with Next Form client navigation.
- **Community navigation:** existing channel sidebar reused in the context slot, protected community image/name, overview/settings access, separate collapsible text/voice groups within existing categories, unread/mention badges and active channels. Community events link selects the community only if present in the authorized event context. Joined communities with no accessible channels show a useful empty state.
- **Chat:** the existing ChannelWorkspaceLayout continues to own its channel and member panes and mobile dialogs. The outer shell contributes only its community rail in the normal desktop channel view; it does not add another persistent global navigation/member panel beside them. Expand sidebar temporarily exposes global destinations. Existing message, composer, thread, search, scroll, receipt and subscription systems are unchanged.
- **Right context:** own profile card, genuine shared-interest suggestions, genuine discoverable new members, preserved friends/member lists and permitted friend updates on global pages. Community overview uses the authorized member directory, up to three existing RLS-filtered post excerpts and relevant published announcements. Text/voice channels keep their existing authorized WorkspaceMembers panel. Unknown, empty and failed reads are shown honestly.
- **Top bar:** community search, real notifications and DM unread count, settings/profile access and the compact activity drawer. At small widths the current profile remains available through navigation/activity rather than squeezing another icon into an overflowing bar.
- **Connection controls:** the original PersistentVoiceBar now includes deafen/undeafen, calling the existing LiveKit context methods. It appears in the global sidebar, community/channel sidebar, mobile bottom bar and a floating desktop panel when global navigation is collapsed. Collapsed-page content reserves space so the panel cannot cover final actions. Room name, microphone, audio state, reconnect/leave and errors are genuine SDK/session state. No provider boundary, token grant, capture stream or worker enforcement is replaced.
- **Brand/theme:** semantic tokens in `src/styles/tokens.css`; authenticated chrome in `src/styles/premium-shell.css`, imported around the existing stylesheet. Exact supplied palette, dark theme, rounded surfaces, cyan selection/focus and existing DM Sans/Manrope/Lucide. The Home hero now uses “Find Your People. Find Your Place.” and shared-interest copy; gaming/Squad Up and Faith & Life remain functional. Public auth/landing/legal/PWA identity are preserved for their later page-design milestone.

## Responsive behavior

Full desktop uses the rail, context navigation and optional activity panel. Activity collapses below 1400px; compact desktop/tablet can collapse secondary navigation or open the navigation drawer. Existing channel members use their existing responsive breakpoint/dialog. Mobile uses one workspace, global navigation/community selection drawer, separate chat channel/member drawers, activity drawer and existing bottom navigation. Existing visualViewport/safe-area/editing handling remains.

Width changes are immediate rather than animating a margin through a horizontal-overflow state. Non-channel mobile pages retain 144px plus safe-area bottom clearance for the navigation/voice bars. The activity drawer explicitly displays its content despite the legacy responsive rule hiding desktop right sidebars. No forced clicks or hidden-overflow masking were used to make tests pass.

## Data and authorization

Shell server actions verify Supabase Auth and use the normal authenticated client. Joined communities come from `member_communities`; thumbnails remain existing RLS-authorized header/cover sources; unread state uses existing `channel_unread_counts` with at most six in-flight community reads. Selected channel/overview context is resolved through RLS and the existing workspace projection. Confirmed community form changes emit an empty local invalidation event: the shell immediately clears old context, advances its request generation and refetches authorized membership/navigation, so leaving cannot retain the old sidebar or resurrect an older pending response. No service-role directory, client-selected actor or client role is trusted.

Existing private personal chat-summary invalidations refresh navigation, with periodic/online repair and generation guards preventing obsolete results from replacing the new route. The rail adds no Realtime client. Member suggestions use `people_search`; community members use `community_member_directory`; post excerpts use existing post RLS; announcements use published audience RLS and optional global/current-community scope. Content is rendered as React text, never untrusted HTML. No email addresses or private file paths enter shell DTOs.

### Small additive read projection for real new members

The previous API did not provide an authorized new-member list. Version **`202611130001_lounge_new_members.sql`** adds only `public.lounge_new_members()`—no tables/columns/backfills, no destructive data changes. It reuses `private.people_visible`, `private.people_card` and live-account/block/privacy checks, excludes self and private/undiscoverable/banned users, returns at most five visible profile cards created within the last seven days, and returns neither email nor exact creation timestamps. Anonymous execute is revoked and reads are rate-limited (30 per 15 minutes/member). Existing public/member/private profile and discoverability choices are preserved.

Only the isolated local stack was updated during implementation. If the function is unavailable or limited, the UI does not invent new members. New-member fallback does not disable chat, existing communities or voice. Shared-interest suggestions and other existing services remain separate reads.

## Deployment and rollback

No new environment variables, provider accounts or media buckets are required.

1. Review/approve release and hosted SQL separately; implementation does not publish or deploy.
2. Apply only pending version `202611130001` through the migration pipeline, or run the entire **`supabase/lounge-members-setup.sql`** in the intended Supabase SQL Editor after approval. It checks the existing Stage 8 prerequisite, records its version, skips recorded reruns and refuses ambiguous objects/history. Do not rerun older phase installers or reset any tables.
3. Verify authenticated new-member reads, anonymous/private/block/banned denials and the intended migration record. Do not use a service-role token as proof of member access.
4. Deploy the reviewed app through the existing Vercel process; confirm Ready and test canonical APP_URL, all navigation, private banners, role boundaries and two real accounts/media devices. The original Supabase/LiveKit/worker configuration remains necessary.
5. Roll the app back normally if required; the additional read-only function can coexist with the previous application. Prefer forward corrections. Any later function removal must be separately reviewed; never drop chat/community/Auth data or replay old schemas as a visual rollback.
